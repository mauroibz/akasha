What changed from the first pass

  • The top half is for today. On now carries every domain you are in the middle of, with the actions you'd take (log a chapter, finish, set aside). Up next is the ranked pile, five deep, one tap to start.
  • The bottom half is the library. One tile per domain: the count, how it splits by status, your score curve, your three best covers, and what's missing. Each tile opens the Library filtered to it.
  • The line survives as the year module: twelve months, your finished covers in place, dashed slots where the goal still needs something, December marked.
  • Everything is a module. The home is a grid of twelve columns. Modules come in sizes, and the layout is stored per user on the server, so it follows you to the phone.

Recommendations

Pick first, then enrich

A source chooses a handful of candidates. Only then do we spend provider calls, and only on those candidates. Nothing crawls a provider to find something to suggest.

This is the order you asked for, and it keeps every provider inside its limits. Today's enrichment job already works this way for items you add. Recommendations add one step in front of it.

SEED

What to start from

One item, when you press More like this. Or your profile: top scores, recent finishes, the pile, what you dismissed.

SELECT

A source picks

Per domain. TMDB's /recommendations for movies and series first. Later, a model call. One request yields a short list of titles with ids and a reason.

STORE

Suggestions table

Title, ids, reason, source, seed, display fields. Home and pages read only from here, never from the network.

ENRICH

Providers fill in

Only the top few, or one you open or mark Want. They go through the domain's own resolve (Wikidata, TVmaze, AniList, Open Library), under the existing budgets.

ANSWER

Your feedback

Want adds it to the pile. Not for me and Seen it are stored and shape the next round.

The shape in code

A domain declares its sources the way it declares enrichment today, so the shared layers never branch on the item type (technical spec 6.6). Sources share one interface whether they call TMDB, a language model or an embedding index. Which provider sits behind a source is configuration.

# domains/movie/__init__.py
recommendation = RecommendationSpec(
    sources=("tmdb",),            # later: "model"
    resolve=resolve_candidate,    # candidate -> item, via the domain's providers
)

# shared: application/recommend.py
class RecommendationSource(Protocol):
    name: str
    def select(self, seed: Seed, profile: TasteProfile,

A guard against made-up titles. A model can name a book that doesn't exist. Its candidates count only once the domain's resolve finds them in a provider; anything that doesn't resolve is dropped and never shown.

The plan

Seven sprints, each one shippable on its own. Home first, because recommendations need somewhere to show up. Then the pile ranking as the quick win. Then the recommendation infrastructure, proven with one domain before it grows.

Home
SPRINT 130

Module grid and the core four. GET /api/home assembles each module's data in one read from existing services. The page at / with On now, Up next (pile in date order until 132), Year, Library tiles and the greeting line. The Library moves to /library.

SPRINT 131

The rest, and Edit home. Lately, Tidy up, One question, Shelves, Lent out. Module sizes, order and visibility stored per user (migration). The phone stack. Walkthrough on your library at 390 and 1440 px.

Quick win
SPRINT 132

Rank the pile. A DEC reversing the recommendations non-goal. A taste profile from scores, score history, rank, shelves, creators and series. Up next ranked with a one-line reason. Something else walks down the list. No network.

Recommendations
SPRINT 133

The infrastructure. The RecommendationSource interface and the per-domain RecommendationSpec in the registry. A suggestions table with seed, source, reason and answer. A recommend job kind with per-source budgets. Endpoints for More like this and for answers. A recorded fake source proves it end to end.

SPRINT 134

TMDB, movies and series. A DEC amending DEC-103. Selection from /recommendations, resolve through Wikidata and TVmaze. The More like this button and sheet, and the Home module. Tested against recorded TMDB responses, not mocks.

SPRINT 135

The model source. An OpenAI-compatible endpoint in configuration, local or hosted. Prompt built from the profile; candidates resolved by each domain's search; unresolved ones dropped. Off until configured.

SPRINT 136

Embeddings. One vector per item from stored text. Similarity re-ranks the pile and the model's candidates, and gives More like this an offline answer from your own library.

Decided and still open

  • Decided: a modular home; reverse the non-goal; the pile ranking as the quick win; recommendations per domain, select then enrich; TMDB first; More like this as a manual trigger.
  • Open, for sprint 134: TMDB's terms ask for its attribution on screen and for cached data to be refreshed within their window. The mock shows the attribution line under each TMDB result.
  • Open, for sprint 135: hosted or local model. A local model on your 3080 keeps your titles and scores in the house, but only works while that machine is on. A hosted one always answers.
